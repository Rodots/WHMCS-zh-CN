# 大型 PHP 语言包无损翻译

## 这套流程在防什么

语言包翻译的失败模式不是「译得不够优美」，而是两个更严重的问题：

1. **文件被译坏。** 一个 `\"` 被换成中文引号 `""`，就可能让整站白屏。PHP 语言包是代码，不是文档；
   译文里的每一个引号、反斜杠、占位符都是语法的一部分。
2. **同一个词前后不一致。** 同一个英文原文在文件里出现多次，译文却是「定价」和「价格」混用。
   几千行的文件必须分片并行翻译，而并行**必然**带来术语分裂——每个执行者独立选词，各自都合理，合起来就乱。

所以本技能的重点不是「怎么译得漂亮」，而是：**怎么把结构损伤变成可检测、可归零的问题。**

## 三条原则

**先证明可切分，再切分。** 整套流程建立在「一个条目 = 一行，且可独立翻译」之上。
如果文件里有跨行字符串、heredoc、或跨行插值，按行切分会**静默**损坏文件——不报错，只是内容错位。
花 30 秒证明均匀性，比事后修复便宜得多。

**令牌多重集是唯一的硬约束。** 必须原样存活的不是抽象的「结构」，而是一组具体令牌：
占位符（`:name` `%s` `{php}`）、转义序列（`\"`）、HTML 实体、HTML 标签、URL/路径。
按**多重集**比较（排序后的列表），因为译文里它们的顺序可以合法变化，但**数量不能变**。

**执行者的自述不是证据。** 分片翻译的子代理会各自写校验脚本、报告「0 issues」——
但脚本是**同一个犯错的 agent** 写的，有盲点。必须用独立的校验工具复核。

## 流程

### 阶段 0 — 预检

```bash
python scripts/langtool.py preflight english.php
```

输出会告诉你：总行数、可翻译条目数、**UNRECOGNIZED 行**、以及令牌清单。

- `UNRECOGNIZED = 0` → 放心分片。
- `UNRECOGNIZED > 0` → **停下来**逐行看。这些行要么是注释/特殊语法（无妨），
  要么是跨行字符串（**按行切分会损坏文件**）。后者必须改用按语法单元切分的策略，不要硬上。
- 同时记下输出的 `lines containing \" escapes` 数量和行号——这些是最高风险行，后面重点核对。

### 阶段 1 — 分片

```bash
python scripts/langtool.py split english.php --size 300 --outdir .work/in
```

`--size 300` 是经验值：大到足够摊平每个子代理的启动开销，小到子代理能可靠地一次写完。
如果单行特别长（>100 字符），适当降到 200。

### 阶段 2 — 写一份契约文件

把 `references/contract-template.md` 复制到 `.work/CONTRACT.md`，填上**目标语言**和**术语表**。

关键：**不要再把规范内联到每个子代理的 prompt 里。** 24 个分片意味着 24 份重复的规范。
写成文件让子代理自己读，既保证每个执行者看到的是**逐字相同**的规则，又只花一次 token。

术语表要在这里定死。凡是文件里高频出现的业务词（Invoice / Client / Ticket / Addon / Domain …），
先在术语表里定一个译法，再让所有分片遵守。**这是预防术语分裂最省力的办法**——
阶段 6 的归一化是兜底，不是首选。

### 阶段 3 — 并行派发

每个子代理负责 2–3 个分片。**在同一轮里全部派出**，让它们真正并行。

每个 prompt 只需要包含：

- 契约文件路径（让它先读）
- 输入分片路径 → 输出路径（一对一）
- 输出行数必须与输入**完全一致**
- 其余交给契约

不要把契约内容重复写进 prompt，也不要在 prompt 里即兴追加规则——那样各分片的规则就不再一致了。

**分片规模要看字节数，不是行数。** 300 行可以只有 16 KB（短条目），也可以有 37 KB（长文案）。
实战中一次 15 个分片的派发里，恰好是最大的那 3 个（33–37 KB）**全部失败**——
子代理写到一半就没了，留下 0 字节或缺文件。补救办法是把大分片再对半切开，
写成 `in_half/h11a.txt`、`h11b.txt`，两个更小的子代理各写一半，
组装前自己把两半拼回 `chunk_11.txt`。派发前先看一眼各分片字节数，
超过约 25 KB 的就预先切半，比事后补跑便宜。

另外：**子代理在写完文件之后失败，文件通常还是好的**。不要因为收到 failed 就丢掉输出，
先按阶段 5 独立校验它——本次 5 个 failed 的子代理里，有 4 个的输出是完全合格的。

### 阶段 4 — 组装

```bash
python scripts/langtool.py assemble .work/out --dst chinese.php
```

会自动对比分片清单里的总行数与实际组装结果，行数漂移会报错。

### 阶段 5 — 独立校验（不可跳过）

```bash
python scripts/langtool.py validate english.php chinese.php --report .work/report.txt
```

**这一步是整套流程的核心价值。** 在本技能的实战验证中：8 个子代理全部报告「校验通过、0 issues」，
独立校验仍然查出 1 处真实的转义引号损坏（`\"` 被写成全角 `""`），以及 86 组术语分裂。
它们自己的脚本没查出来，因为盲点来自写脚本的人。

看两个数字：**hard problems 必须为 0**，`possibly untranslated prose` 需要人工扫一眼确认都是品牌名/URL。

### 阶段 5b — 同语言字形转换的额外校验（zh_TW → zh_CN 等）

英译中时，`validate` 的 0 基本等于「没问题」。**同语言字形转换不是。**
原文已经是中文，结构可以完美无缺，而字形根本没换干净——`validate` 对此一无所知。
这种情况必须再跑两个独立工具：

```bash
python scripts/residue.py chinese_zh_tw.php chinese.php --report .work/residue.txt
python scripts/terms.py   chinese.php --report .work/terms.txt
```

- `residue.py`：逐字判断繁体残留（需要 OpenCC）、检查纯英文条目是否被越界改写
  （`pure-English values modified` 必须为 0）、列出仍然活着的台湾用语（提示项）。
- `terms.py`：`candidates` 抓不到的同义竞争词（两种「Ticket」写法、两种「Add」写法）。

判定繁体只能**逐字**做：`OpenCC('t2s').convert(ch) != ch`。
拿简体词表去匹配整条字符串会把正确译文全判成错——本次实战中一个子代理就是这么误判、
进而放弃了该项检查。

完整流程、两岸用语对照表和交付清单见 `references/zh-tw-to-zh-cn.md`。

### 阶段 6 — 跨分片一致性归一

分片并行必然产生同源异译。先看全景：

```bash
python scripts/langtool.py candidates english.php chinese.php > .work/divergent.json
```

这是一张 `英文原文 → {各译文: [行号]}` 的清单。**逐条判断，不要无脑取多数**——
多数派有时是错的。把你确定的术语写成覆盖表：

```json
{
  "Pricing": "定价",
  "Active": "已启用",
  "Recurring": "循环"
}
```

然后归一：

```bash
python scripts/langtool.py normalize english.php chinese.php --map .work/canon.json --log .work/norm.log
```

工具会给同一英文原文强制统一成一个译文，并且带**安全护栏**：
如果候选译文与要覆盖的译文的占位符/转义数量不一致，就**跳过并在日志里报告**，
绝不静默改写可能改变语义的内容。事后一定要看 `skipped` 列表——那里往往藏着真实缺陷。

**没有写进 `--map` 的同源异译，工具会自己按「多数派 + 确定性 tiebreak」统一——这个默认值可能选错。**
本次实战中，`停權原因` 因为没进 map，被自动统一成了「封禁原因」（tiebreak 按字符串序取），
而它同时用在 `suspendreason`（服务暂停）上，正确译法是「暂停原因」，事后才改回。
所以：**要么把每组都写进 map，要么在 normalize 之后重新跑一遍 `candidates` 并核对
「工具替你做了哪些决定」**。真正语义不同、应当保留分叉的（如 `bannedbanreason` 与
`suspendreason`），要在交付说明里写明这是有意为之。

### 阶段 7 — 判定报警项

再跑一次 `validate`，此时 hard problems 应为 0。剩下的**实体差异是提示，不是错误**。
典型情况见 `references/adjudication.md`：`&amp;` 作为英文连词 "and" 时，中文里本该被吸收成「及」「并」，
强行保留实体反而别扭。**报警项要人工裁决，不要盲目「修复」**——盲目修复会引入真正的问题。

### 阶段 8 — 交付

```bash
python scripts/langtool.py lexcheck chinese.php
```

逐行扫描字符串字面量的引号配对与转义，能抓住未闭合字符串、裸引号提前终止等致命错误。
**本机若有 PHP，一定再跑一次 `php -l chinese.php`**，词法检查不能替代真正的解析器。

交付说明里要主动交代三件事：

- **语言代码行**（如 `$_ADMINLANG['locale'] = "en_001"`）通常按规范保留原值，但部署时往往需要改成 `zh_CN`。
  明确告诉用户，让他决定。
- **有意未翻译的内容**：品牌名、URL、格式串（`MM/YY`）、示例域名。列出来，避免用户以为是漏译。
- **被吸收的 HTML 实体**（如 `&amp;` → 「并」），说明原因，给出改回的方式。

## 工具速查

### langtool.py（结构）

| 子命令 | 用途 |
|---|---|
| `preflight <src>` | 判断能否安全分片 + 令牌清单 |
| `split <src> --size N --outdir D` | 按行切分 |
| `assemble <dir> --dst F` | 合并回去，校验行数 |
| `validate <src> <dst>` | 六类结构不变量对比（核心） |
| `candidates <src> <dst>` | 列出同源异译清单 |
| `normalize <src> <dst> --map M` | 强制术语统一（带护栏） |
| `lexcheck <dst>` | PHP 字符串字面量词法检查 |

非 `$_ADMINLANG` 的变量名或不同的语法形状，用 `--pattern` 传入带 `prefix` / `value` 命名组的正则。
默认模式同时兼容 `$_ADMINLANG[...]`、`$lang[...]`、`$LANG[...]` 等。

退出码：`0` 干净 / `1` 发现问题 / `2` 用法或 IO 错误。可以直接在脚本编排里用。

### residue.py / terms.py（语言，仅同语言字形转换需要）

| 命令 | 用途 |
|---|---|
| `residue.py <src> <dst>` | 繁体残留（OpenCC 逐字）、纯英文条目被改写、竞争用语 |
| `terms.py <dst>` | 同义竞争词计数（`candidates` 看不到的那一类） |

两者都支持 `--report`、`--pairs-file`（自定义词表），`--pattern` 与 langtool 一致。
`residue.py` 需要 OpenCC：设 `OPENCC_PYTHONPATH` 指向解压出来的 wheel 目录即可
（pip 被沙箱挡住时的绕过办法见 `references/zh-tw-to-zh-cn.md`）。

## 常见陷阱

- **全角引号替换 `\"`**：最隐蔽的杀手。它有时仍是合法 PHP（全角引号不是定界符），
  所以文件能解析、页面能开，但数据已经错了。永远用 `\"` 数量奇偶校验抓它。
- **正则贪婪吞掉标点**：URL 匹配要排除 CJK 与全角标点，否则 URL 末尾的 `）` 会被算进 URL，
  产生假报警。
- **把裸 URL 当漏译**：值为 `http://example.com/callback` 的条目没有可翻译内容，
  保持原样是**正确**的。
- **忘了检查空值**：`""` 是合法的空条目，必须原样保留，别当解析失败。
- **归一化过度**：不要把语义不同的近似原文强行统一。工具按**精确字符串**分组，这正是为了安全。
- **结构 0 问题 ≠ 翻译完成**（同语言字形转换）：`validate` 完全不看字形。
  没有 `residue.py` 这一层，一个 3941 行全改、结构完美、却残留 10 个繁体字的文件会被判为合格。
- **用词表匹配整句来查繁体**：简体词里也有与繁体同形的字，这样查会满屏假阳性。
  只能逐字 `OpenCC('t2s').convert(ch) != ch`。
- **子代理自写的校验脚本有系统性盲点**：本次 13 个分片里有 2 个自报「繁体残留 0」，
  独立检查却查出 `現`×8、`窺`、`齊`。它们的脚本用的是错的判定方法。
  **自述永远不能替代独立工具。**
- **纯英文条目不是漏译**：语言包里本来就有的、尚未本地化的英文条目，
  在同语言转换任务中必须逐字节保留；误改会让交付物与源文无法对应。

## 实战验证过的证据

### 一、英译中（7058 行，英文 → 简体中文）

- 分片/组装往返**字节级一致**（636031 B 输入 → 636031 B 输出）。
- 最终校验：行数 7058 = 7058，键名差异 0，占位符差异 0，转义差异 0，标签差异 0，URL 差异 0。
- 独立校验抓出 1 处 `\"` → 全角引号损坏（子代理自检未发现）。
- 归一化处理 86 组术语分裂、改写 97 行，**0 次**因令牌不一致被护栏拒绝。

### 二、同语言字形转换（4473 行，繁體 zh_TW → 简体 zh_CN）

- 预检 `UNRECOGNIZED = 1`，是 `if (!defined("WHMCS")) die(...)` 守卫行（无害），
  其余 4469 行全部是自包含单行条目 → 按行切分安全。
- 15 个分片 × 300 行；其中 3 个大分片（33–37 KB）的子代理失败，改为 150 行对半切分后全部成功。
- 最终独立校验：**行数 4473 = 4473**，键名/结构差异 0，`\"` 差异 0，占位符差异 0，
  HTML 标签序列差异 0，URL 差异 0，**HTML 实体差异 0**；无 BOM、LF 不变、3944 行值被改动。
- `residue.py` 抓出子代理漏掉的繁体残留 10 处（`現`×8、`窺`、`齊`）并修正；
  最终 `residual traditional chars = 0`、`pure-English values modified = 0`。
- `candidates` 找出 26 组同源异译，归一化改写 28 行，**0 次**触发护栏；
  其中 1 组（`停權原因`）因未写进 map 被工具默认统一错，事后改回「暂停原因」——
  这条经验已写进阶段 6。
